DTO（Data Transfer Object，数据传输对象）并不属于某一个单独的纵向执行逻辑层，而是作为跨层流转的数据契约（Contract），在企业级架构中主要服务于表现层（Handler）与业务逻辑层（Service）之间的边界交互。
它在项目物理目录中归属于 models/dto 模块，充当外部网络世界与内部业务核心之间的“隔离舱”。
1. 用法（Usage）
在请求与响应的生命周期中，DTO 分为两个流向：
请求 DTO（Request DTO，如 RegisterReq、LoginReq）：
入口：在 Handler 层被 Axum 的 Json(payload) 反序列化并执行格式校验（payload.validate()?）。
去向：校验通过后，作为业务入参传递给 Service 层的函数（例如 service.register(payload)）。
响应 DTO（Response DTO，如 UserResp、LoginResp）：
来源：Service 层完成业务处理并从 Repository 拿到数据库实体（User Entity）后，将实体数据清洗、脱敏，组装为响应 DTO。
出口：返回给 Handler 层，Handler 将其包装为 HTTP 响应体并序列化为 JSON 发回给前端。
2. 设计理由（Design Rationale）
安全脱敏隔离：
数据库实体 User 包含 password_hash、two_factor_secret、deleted_at 等高度敏感或系统内部的字段。如果直接将数据库实体序列化返回给客户端，极易导致安全隐患。
借助 UserResp，对外只暴露 id、name、email 等公开安全的字段，屏蔽底层机密。
解耦数据库架构与前端展示：
数据库的表结构是围绕存储范式、索引和性能设计的；而前端请求和响应是围绕界面交互与用户体验设计的。
若直接用 Entity 当参数，数据库改动任何字段（如分表、重命名字段）都会直接破坏前端接口契约。通过 DTO 作为缓冲层，即使底层数据表结构发生变更，对外暴露的 API 结构依然可以保持向后兼容。
3. 优缺点分析（Pros & Cons）
优点：
契约纯粹：明确规定了接口接收什么、返回什么，配合 Swagger/OpenAPI 可直接生成清晰的接口文档。
边界防御前置：字段注解校验（validator）只用写在 DTO 上，不污染底层数据库实体模型。
缺点：
对象样板代码增多：在 Entity 和 DTO 之间需要编写映射转换代码（如 impl From<User> for UserResp）。
